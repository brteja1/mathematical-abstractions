# Quota service specification

Status: engineering proposal, not approval to replace stakeholder promises. Clause IDs below are stable. The source goals are TASK.md, stakeholder bullets R1–R6; the environment is TASK.md, opening two paragraphs. No production service is included.

## Original goals and interpretation

**G-ENV.** Two honest, noncrashing replicas A and B start empty; global capacity is 10 integer units. Partitions may last arbitrarily long; messages may be delayed without bound, duplicated, or reordered. Both replicas can perform local work. Distinct logical requests have globally unique IDs; an identical delivery is a retry. These assumptions admit, for example, an empty, permanently partitioned execution and are themselves compatible.

| Source ID | Preserved stakeholder request | Quantification / observation |
|---|---|---|
| R1 | Outstanding accepted reservations across both replicas never exceed 10; success cannot be revoked by reconciliation. | All executions and every instant; count distinct logical IDs once, not copies at replicas. |
| R2 | Either isolated replica with no local reservations immediately succeeds for any fresh amount 1–10; only exceeding local usage 10 permits rejection. | Each replica, every such input, including simultaneous distinct requests. “Immediately” means no remote dependency, not a supplied CPU deadline. |
| R3 | Same-ID retries consume no extra capacity, including at the other partitioned replica; a different amount under that ID is an error. | Identity is exact ID equality, not amount equality. Original text does not specify a cross-replica response deadline for detecting an amount conflict. |
| R4 | Valid releases are idempotent; reserve retries and reconciliation cannot resurrect released reservations; IDs are never reused. | Release is of a previously accepted logical ID. Unknown-ID release behavior is unspecified in the original. |
| R5 | Eventual message delivery yields replica agreement; additionally agreement within 100 ms of partition end. | Separate eventual convergence from the wall-clock deadline. Continuous new writes require a per-update interpretation; stable total equality requires quiescence. |
| R6 | Delete old request/release metadata after one hour without losing safety even with arbitrarily late messages. | Literal deletion of all distinguishing evidence is analyzed below. Compaction retaining equivalent information is a different policy. |

## Findings before policy decisions

**F-CAP (demonstrated conflict: R1 + R2 + G-ENV).** Partition the empty replicas. Submit distinct IDs x and y, each of amount 10, to A and B respectively, with no intervening release. R2 forces both successes, hence outstanding usage 20, violating R1. Each local execution is indistinguishable from being the sole requested replica. Any randomized implementation promising safety on every execution must also handle this allowed execution. Revoking a success later violates R1. Deduplicating IDs does not help because x ≠ y. This argument quantifies over implementations; it is stronger than a counterexample to one algorithm. No minimal-core claim is made.

**F-TIME (unachievable deadline: R5 deadline + G-ENV).** Let A accept x while isolated and B remain unaware. The partition ends at t=0, but the update arrives at t=101 ms. This is eventual delivery permitted by the environment. B cannot distinguish whether x exists before that delivery. A cannot discard an accepted promise. Therefore no unconditional 100 ms agreement guarantee follows. A timed SLA would require end-to-end bounds including queueing, catch-up backlog and scheduling, not merely a partition-end signal.

**F-GC (conditional information-loss conflict: R4 + literal R6; also retry semantics R3).** Accept x, release x, delete every record distinguishing x from a fresh ID after one hour, then receive its original reserve. Accepting it resurrects x. An empty-history state presented with the same input must still support a fresh request (R2); the indistinguishable states require different outcomes. Universally rejecting unknown IDs avoids resurrection only by changing fresh-request availability. A permanent seen-ID set, closed-epoch marker, or retained tombstone defeats the indistinguishability premise but is retained metadata. Thus a one-hour cache TTL alone is unsafe; this is not a claim that every kind of compaction is impossible. `checks.py` demonstrates the naive forget-and-accept failure; the indistinguishability argument supplies the broader conditional conclusion.

**F-IDENTITY (ambiguity / coordination requirement, not an independent unconditional contradiction).** During isolation B cannot know whether unseen ID x was already bound to amount 4 at A. Accepting x with amount 7 as a new reservation would violate R3 if that binding exists. Immediate, globally accurate amount-conflict classification cannot be promised at B without coordination or an additional binding scheme. R3 does not explicitly require such immediate classification, so the proposal defers it while unavailable.

**F-ORDER (protocol obligation).** Idempotent set insertion alone does not protect a release: a delayed active record can overwrite a deleted record. This is a failure of that merge design, not an impossibility of R4. Ordered authoritative replay and permanent terminal states below prevent it.

## Necessary decisions and recommended replacements

**D-POLICY.** Recommend preserving irrevocable global safety R1, identity R3, release safety R4, and eventual convergence from R5. Replace R2 by a single-authority policy: A alone decides mutations. B forwards or explicitly reports temporary unavailability. Even an empty isolated B cannot accept a fresh reservation. A can accept locally up to the global limit. This is an intentional loss of symmetric partition availability, not fulfillment of R2. Fixed escrow (for example 5 units each) is another possible policy, but also fails original R2; it is not the protocol specified here.

**D-TIMING.** Replace the R5 100 ms promise with conditional eventual convergence and a nonbinding operational latency target. No numerical completion deadline is promised.

**D-RETENTION.** Replace R6 with indefinite retention of ID-to-amount bindings and terminal decisions, including releases and capacity rejections. Old log payloads may be compacted only into an equivalent complete snapshot. No one-hour deletion of deduplication information is allowed. Storage grows with distinct IDs. Finite storage cannot promise unlimited fresh admissions forever; deployment must provision/archive this index or introduce a separately reviewed API limit/epoch policy. Storage failure must never produce a success without a committed record. This proposal assumes sufficient storage for the supported workload, without claiming bounded metadata.

**D-ASSUMPTIONS.** No failover, leadership election, authority transfer, or A replacement is supported. A's serialized state is available to its local handler throughout this noncrashing model. Each local transaction terminates under fair scheduling and sufficient resources. After connectivity returns, retries/anti-entropy are fairly serviced, each committed event eventually reaches B, and B eventually processes it. Client completion additionally needs eventual request and response delivery. No wall-clock bounds follow. These scheduling/resource assumptions are explicit additions for progress, not consequences of safety.

## Proposed implementable contract

**P-STATE.** For one customer, authority state is a finite map M from nonempty finite byte-string IDs to `(amount, decision, phase)`. Amounts are mathematical positive integers, implemented with checked arithmetic or compared against 10 before addition. `decision` is ACCEPTED or CAPACITY_REJECTED. Phase is ACTIVE or RELEASED for ACCEPTED, and REJECTED for CAPACITY_REJECTED. Each ID is absent initially. Define U(M) as the sum of amounts for ACTIVE entries. There are no expirations or implicit releases. An ID's first well-formed reserve processed by A binds its amount permanently, including a rejected request. Global uniqueness is a client obligation; conflicting payloads are handled even if clients violate it. First means A's serialization order, not send time.

A also holds an append-only logical event sequence L and its sequence number n, initially empty/0. Each event contains its sequence number, ID, amount, decision and new phase. B holds an applied contiguous prefix length k, materialized map MB, and an out-of-order event buffer indexed by sequence number. Initially k=0, MB empty, buffer empty. A's map is the authoritative logical reservation state; B's map is a copy and is never additional capacity. There is only one logical allocation limit of 10, never a per-replica independent allowance.

**P-API.** `reserve(id, amount)` accepts positive integers of any magnitude; amount >10 is a capacity rejection for a fresh ID. Invalid encoding, empty ID, noninteger or nonpositive amount returns INVALID_ARGUMENT without binding or changing state. `release(id)` accepts an ID, not a new amount. Authenticated customer scoping is assumed at ingress; cross-customer authorization is outside this single-customer model. There is no extra release token requirement. Requests at B are forwarded to A; B must not answer mutations from its stale map. At A, one lock/serial executor covers lookup, capacity test, map mutation and log append; the response is emitted only after that transaction commits. Concurrent requests are ordered by this executor.

**P-RESULT.** Reserve outcomes at A are ACCEPTED_ACTIVE(id, amount), ALREADY_RELEASED(id, amount, originally_accepted=true), CAPACITY_REJECTED(id, amount), ID_AMOUNT_CONFLICT, or INVALID_ARGUMENT. Each authoritative response also carries the current committed sequence n observed at its transaction boundary, so clients can request a replica prefix at least that new. ACCEPTED_ACTIVE creates or confirms exactly one outstanding promise. ALREADY_RELEASED confirms historical acceptance without creating a new promise. Retrying after release deliberately reports current terminal status rather than replaying a misleading ACTIVE response. A CAPACITY_REJECTED decision is terminal for that ID: after capacity frees, a new logical attempt requires a new ID. Concurrent conflicting amounts bind whichever well-formed request A processes first; the other gets ID_AMOUNT_CONFLICT regardless of current phase or capacity.

Release outcomes at A are RELEASED (also for repeated releases), NOT_ACCEPTED (unknown or capacity-rejected ID), or INVALID_ARGUMENT. NOT_ACCEPTED does not bind or cancel an unknown ID. A release reordered before its reserve is therefore not a valid release of an accepted reservation; the client must wait for acceptance and retry release if necessary. Once a reserve commits, a subsequent release processed by A is valid even if replication or its reserve response is delayed.

**P-UNAVAILABLE.** Either ingress may return UNAVAILABLE when it cannot obtain an authoritative result; for an isolated B it may do so without waiting for the partition to end. This is an explicit retryable transport/service outcome, not a logical capacity rejection and not evidence of absence or conflict. A request forwarded before a timeout may already have committed. Clients must retry the same ID and amount, never infer failure and substitute a new ID automatically. No deadline is promised for a remotely dependent operation. A delayed response may describe a past linearization point; a delayed ACCEPTED_ACTIVE received after release does not resurrect the record or authorize a new allocation. Status/response correlation must preserve IDs.

**P-RESERVE.** Atomic transition at A for a well-formed input `(i,a)`:

1. If i is present and its amount differs from a: return ID_AMOUNT_CONFLICT, no mutation.
2. If i is present with equal amount: return its mapped reserve outcome under P-RESULT, no mutation and no event.
3. If i is absent and U+a ≤10: insert ACCEPTED/ACTIVE, append that event, return ACCEPTED_ACTIVE.
4. Otherwise insert CAPACITY_REJECTED/REJECTED, append that event, return CAPACITY_REJECTED.

**P-RELEASE.** Atomic transition at A: absent or REJECTED returns NOT_ACCEPTED without change; RELEASED returns RELEASED without change; ACTIVE changes once to RELEASED, appends a release event, and returns RELEASED. Capacity is freed at this commit, not at delivery to B. Metadata is retained. A release never subtracts capacity twice.

**P-REPLAY.** A continuously retransmits missing committed log entries in anti-entropy; B acknowledges only its contiguous prefix. Delivery to B of sequence j≤k is ignored. Delivery j>k is buffered (duplicates overwrite with the identical event); apply k+1 repeatedly when present. Applying an event updates the specified map entry and advances k. Events cannot be fabricated by clients. Conflicting content for one sequence number signals an integrity/protocol fault: stop applying and alert; never choose a winner by wall-clock time. Capacity rejections and bindings replicate too. Only A produces events, so legitimate conflicting versions do not exist. Stale reserve events cannot override a release because B never reapplies an earlier sequence. B never sends its materialized state as a write to A.

**P-SNAPSHOT.** Optional log compaction creates a complete snapshot `(n,M)` from a consistent A transaction boundary. It must preserve every ID, binding, rejection and release. B installs only snapshots with n>k, sets k=n and MB=M, drops buffered entries ≤n, then replays larger contiguous entries. Ignore older/equal snapshots. Authority log payloads through n may be removed only once that complete snapshot is available for future catch-up; retained snapshots/indexes cannot lose deduplication facts. Snapshot installation is atomic. Indefinite full-log retention is the baseline; snapshot optimization is not modeled in checks.py.

**P-INVARIANTS.** Every reachable authoritative state satisfies:

- I-CAP: 0≤U≤10. Outstanding accepted promises are exactly ACTIVE logical IDs in M, counted once.
- I-ID: every ID has at most one permanently bound amount and one initial decision; identical retries have no capacity effect.
- I-TERM: RELEASED never becomes ACTIVE, and REJECTED never becomes accepted. Only an explicit valid release ends an accepted promise.
- I-LOG: replay(L)=M; MB=replay(L[1..k]), 0≤k≤n. B's stale state is never used to allocate or release global capacity.

Proof sketches, distinct from experiments: initially all invariants hold. The sole capacity-increasing transition checks U+a≤10 under the same lock; release decreases U once; all retries/errors are unchanged states. Bindings are inserted once and never replaced. Terminal-phase rules prohibit resurrection. Each mutation and corresponding log append are atomic. Induction over B's contiguous replay establishes I-LOG despite arbitrary delivery order and multiplicity. These are engineering induction arguments, not machine-checked proofs or a proof of implementation conformance.

**P-CONSISTENCY.** Completed authoritative mutations are linearizable at A's transaction boundary; B-origin mutations have that same boundary after forwarding. UNAVAILABLE results permit an unresolved operation that may later be found committed. B may expose explicitly labeled stale reads with prefix k; authoritative reads must go through A and may be unavailable. Clients requiring read-your-writes must query A or wait for B to reach the returned commit sequence. This is not a multi-writer merge protocol. Under D-ASSUMPTIONS every fixed committed prefix eventually appears at B. After finitely many mutations and eventual delivery/processing, both maps become equal permanently. Under continuing writes, per-event propagation is guaranteed, not simultaneous equality forever or bounded staleness. There is no guarantee of agreement during a permanent partition.

**P-LIFECYCLE.** Never reuse request IDs. Retain all decisions, amounts and release tombstones indefinitely, or an exactly equivalent complete index. A one-hour operational response cache may expire, but lookup must then consult this index. No timestamps or TTLs determine logical validity. Epoch expiry, bounded message age, client watermarks and finite ID quotas would change the API/environment and are not assumed by this proposal.

## Acceptance scenarios

| ID | Input / schedule | Required proposed result |
|---|---|---|
| E1 | Empty A receives x:10 while partitioned; B receives distinct y:10. | A accepts x; B returns UNAVAILABLE. If forwarded later while x active, y is CAPACITY_REJECTED. Explicit R2 replacement. |
| E2 | Empty A receives x:6 then y:5. | x accepted, y terminal capacity rejection; U=6. |
| E3 | Retry x:6 at A or B. | At A same acceptance without more capacity; B forwards or UNAVAILABLE, never allocates locally. |
| E4 | x:6 exists; retry x:7. | A returns ID_AMOUNT_CONFLICT even after release; isolated B defers via UNAVAILABLE. |
| E5 | Release active x twice; delayed reserve x:6 arrives. | Both releases RELEASED; retry ALREADY_RELEASED, U remains unchanged. |
| E6 | B receives release event #2 before acceptance #1, then receives #1 and duplicate #1. | Buffer #2; apply #1 then #2; duplicate ignored; x remains RELEASED. |
| E7 | Unknown z released, then reserve z:1 arrives. | NOT_ACCEPTED then acceptance if capacity; earlier release was not valid acceptance-based release. |
| E8 | x:10 accepted; y:1 rejected; release x; retry y:1. | y still rejected. New ID z:1 can succeed. |
| E9 | x was released years ago; old reserve/release/messages arrive. | ALREADY_RELEASED / RELEASED / stale-event ignore; no resurrection. |
| E10 | Fresh amounts 0, -1, fractional, or malformed ID; fresh amount 11. | Invalid arguments cause no binding; 11 gets recorded capacity rejection. |
| E11 | Opposite-order requests x:6 and x:10 arrive concurrently. | Exactly one initial binding in A's order; other amount gets conflict. |
| E12 | Partition heals but an update takes 101 ms to arrive. | Temporary disagreement allowed; eventual catch-up required, no 100 ms promise. |

## Mathematical mapping and verification boundaries

**V-MAP.** Catalog retrieval uses the dependency-free `python3 catalog/scripts/catalog.py` backend. No external sources or catalog edits are needed. `urn:csabs:concept/LabelledTransitionSystem`, its `urn:csabs:axiom/LabelledTransitionSystem-labelled-steps` and `urn:csabs:axiom/LabelledTransitionSystem-finite-paths`, and operations `urn:csabs:operation/LabelledTransitionSystem-postAction` / `urn:csabs:operation/LabelledTransitionSystem-traces` map S to `(M,L,k,buffer)`, I to the singleton empty state, and labels to reserve/release/deliver/no-op actions. Equality is exact tuple/map equality. BFS computes action successors and finite reachable paths; original counterexamples are explicit finite action traces. These defining rules allow infinite carriers and do not imply fairness or correctness of this particular protocol.

`urn:csabs:concept/LinearTemporalLogic`, operation `urn:csabs:operation/LinearTemporalLogic-satisfies`, and axiom `urn:csabs:axiom/LinearTemporalLogic-derived-modalities-and-models` supply notation G(I-CAP ∧ I-ID ∧ I-TERM ∧ I-LOG), and for each committed event e, G(committed(e) ⇒ F appliedB(e)), conditional on D-ASSUMPTIONS. Infinite executions include stuttering/delivery delays; time positions are steps, not milliseconds. These formulas state obligations; checks.py does not run an LTL checker or prove fair liveness.

SafetyProperty / LivenessProperty were consulted for classification only; their records disclose `legacy-source-missing`, so no sourced theorem or compiled proof is attributed to them. Selected LTS/LTL records are editorial formulations, not machine-checked witnesses. No catalog law or Lean theorem is imported as evidence for this protocol.

**V-SCOPE.** checks.py is the complete dependency-free finite transition model plus targeted traces; Python is an intentional backend choice, not a fallback claimed to be an unavailable solver. No Lean/TLA+/Alloy/Z3 proof is claimed. Finite exploration covers exactly two IDs, reserve amounts {6,10}, all reserve/release/delivery interleavings, and arbitrary retry/duplicate self-loops via collapsed state equality. Each ID has at most an initial event plus one release, so log length ≤4 without a depth cutoff. It tests safety and that catch-up is possible from every reachable state after quiescence; fairness-based universal progress remains the protocol argument above. Separate examples cover integer amounts 1–10, 11, argument validation, binding conflicts, cross-ingress behavior and terminal rejection. It omits snapshots, real persistence, resource exhaustion, actual network code and wall-clock performance. A successful run is evidence only for these domains. The source requirements are not jointly realizable; the proposed repair has a nonempty initial state and supports both acceptance and rejection without hiding the required conflicting scenario.
